# Verification

Run from the repository root on macOS with Xcode/Swift 6.2 or later, Python 3.11+ and Node.js 24+. CI selects Xcode 26.3, Python 3.13 and Node.js 24 explicitly; actions are pinned to immutable revisions. Local builds honour DEVELOPER_DIR. All first-party targets use Swift 6 language mode. Test and release builds treat warnings as errors; the verifier also rejects first-party SDK-boundary warnings that the compiler leaves as warnings. The formatter omits the multiline-string reflow option because older and newer Swift toolchains encode its default differently.

```sh
python3 Scripts/check_repository.py
python3 -m unittest discover -s Scripts -p 'test_*.py'
node --test Scripts/test_site.cjs Scripts/test_score.cjs Scripts/test_editor.cjs
./verify.sh --tests-only
./verify.sh --skip-accessibility --skip-audio-output  # macOS CI with WindowServer
./verify.sh --skip-accessibility --skip-audio-output --preview-jobs 4  # two isolated static pairs
./verify.sh
```

The first command checks public-repository hygiene (including new nonignored files), vendor hashes, license policy, dependency pins, package-wide Swift 6 mode and website links, and generates `.verification/cadence.cdx.json`. Gitleaks is a separate gate (`Scripts/scan_secrets.sh`). The full native workflow builds a fresh release app and stages a separate instrumented debug app from the matching unit-test build. It verifies both with the same deterministic scenarios, ad hoc signatures, renderer assertions and original fixtures. It produces logs, JSON assertions and screenshots in `.verification`, not Git. It fails on a missing or stale report.

## Iteration time

The repository job always runs policy, website, Python/JavaScript, secret and advisory checks. A change confined to `Docs/`, `site/` and named root documentation files skips the Mac job. App sources/tests, resources, dependencies, licenses, scripts and workflow changes require the full native gate. The diff disables rename detection so moving an app source into documentation cannot hide its deletion. Unknown events, incomplete history, empty diffs and manual dispatch select full verification. A skipped Mac job does not claim fresh native coverage; it only states that app/check inputs were unchanged.

CI overlaps two isolated production/instrumented preview pairs, at most four app processes at once. Each retains its own in-memory preview state, process group, output files and coverage destination. A batch waits for all of its captures; an exception still joins every other bounded process and retains successful pairs before reporting failure. Device self-checks, first-launch checks and accessibility actions remain serial because they own input/focus resources. The editor navigation round trip also stays serial: it deliberately tears down and recreates WebKit views, and its hosted renderer result did not remain reliable under concurrent launch load. Both builds still execute every scenario. The driver passes each scenario’s required renderer and activity assertions to the native snapshot host. After the preview’s framing delay, capture waits up to 25 seconds for that same report to become ready; missing notation cannot hide behind completed domain checks. The final external validator still checks every assertion. A deadline writes the incomplete sidecar and fails, without retrying the scenario. The full-study renderer also runs before the long matrix to catch this boundary early. `--preview-jobs 1` is the default for local diagnosis; `summary.json` records the selected concurrency and each pair's wall time. Native assertion/log artifacts include the instrumented build as well as production.

Swift compilation is cached only within a fingerprint covering the runner image, OS build, architecture, Xcode/Swift versions, checkout path, dependency pins and compiler configuration. Unit compiler flags live in `Scripts/swift_build_config.py`, shared by the verifier and cache fingerprint; changing screenshot scheduling does not discard compiled Swift. A source manifest restores timestamps only for byte-identical files, avoiding a full rebuild merely because checkout refreshed their dates. Changed files keep their fresh timestamps and Swift's incremental dependency checks still run. No saved cache represents a passing test run: unit tests, native checks, signatures, resource comparisons and source inventories execute again. Raw profiles and unit coverage exports are removed before cache upload and independently before every unit run. Only `.verification/build` is cached, never Keychain, environment files, user music, application state or native coverage evidence. Cache absence is a normal cold build; GitHub's branch-scoped caches keep pull-request writes out of the default branch's cache scope. Do not broaden the restore prefix across toolchain or build-flag changes.

## What tests establish

Core tests cover musical happy paths and meaningful failure/adversarial cases: invalid pitches/notation, archive traversal and oversized entries, unsupported transcription, injected provider errors, persistence conflict/corruption, stale reviews, assisted versus independent evidence, MIDI timing and cancellation. Native state tests check save/retry and feature integration. Owner tests cover disk conflicts, corruption, failed commits without publication, missing pieces with retained notes, size/identity limits, legacy snapshots and observation forwarding. Signing tests reject development certificates, missing timestamps/runtime, debugger entitlements, failed notarisation and missing tickets. Website controller tests run real code with silent fake audio and cover visible/sounding pitch agreement, bass harmonics and isolated-bass comparison, cancellation while audio resumes or listening mode changes, stop, completion and unavailable sound. Original fixtures keep the workflow independent of paid models or private books.

Coverage is measured separately for **MusicCore** and the **Cadence app**, with distinct unit-only and combined native-workflow results. The core has a 90% line-coverage floor; the three workspace owners retain 85% and the changed learning/import orchestration retains 80%. The complete app has a 12% unit-only floor and a 50% combined floor. Combined device/request owner coverage must reach 80%. These are regression gates, not claims that every important behaviour is covered. Every first-party source file, including views and diagnostics, must appear in the inventory. Native execution coverage does not establish assertion quality, accessibility or musical accuracy by itself.

Before unit tests, remove old raw profiles as well as old exports so filtered runs cannot inflate a later full run. Full verification captures a unique profile for every instrumented app process, merges it with a copied unit profile and exports against copied matching binaries. Release binaries are tested separately and are never mixed into debug profile mappings. Hashes bind the objects, unit export and unit profile; fresh timestamps and expected process counts guard collection. LLVM warnings, missing sources and source/test changes during verification fail the run. `summary.json` keeps the existing `coverage` field as unit-only coverage (also labelled `unitCoverage`) and adds a separately named `combinedCoverage`. It also records native scenario results, skipped checks, toolchain and input digests. The per-file HTML report lives under `.verification/native-coverage/<run-id>/html/index.html`.

## Before release

Inspect representative screenshots at compact and large sizes: practice home, full score/editor, library, import/review, piano/guitar activities, general/AI/about settings and storage failure. Confirm focus/labels, selection semantics, discoverable exits, readable disabled reasons, score context and stop behaviour. Update the guide whenever actual controls differ from its instructions.

Manually test a connected MIDI keyboard, microphone permission denied/granted, audio-device changes, different display scaling and VoiceOver. These are explicit manual gaps if no hardware or accessibility session was used; do not label virtual MIDI as physical testing.

## Learning journeys and accessibility actions

The first complete journey has core and native tests for original piano/guitar scores, scoped evidence, common-tone recognition, a multi-answer opening, starting-shape verification, interrupted MIDI, whole-progression completion, failed saves and idempotent retry, current-source guards, an eight-bar creative artifact and delayed transfer to the other piece. Received PDF replies have explicit save-only retry tests, including disk conflicts and stale/cancelled results. No paid model requests are required.

Full verification requires an unlocked macOS session and Accessibility access for the invoking developer terminal; the external runner fails clearly if a connection is unavailable and never changes system permissions. A locked session can still render screenshots while refusing accessibility requests. A quick `--tests-only` run needs neither desktop controls nor output playback. macOS CI runs the native previews and combined coverage with `--skip-accessibility --skip-audio-output`: the report explicitly lists the unexecuted accessibility scenario and four live output checks. Offline synthesis, sampler rendering, virtual MIDI, storage and renderer checks still run. Neither skip option can hide another failure or claim a device result.

Full verification includes native course-map previews at compact/large sizes and for both instruments. The isolated `--song-preview --song-ax` scenario uses actual accessibility controls to answer incorrectly, retry with support visible, select the arrangement chapter, verify an unfinished arrangement cannot be finished, open its eight bars, return to the map and open the full source piece. The runner also opens the contextual coach beside the full score, enters a question through the accessibility text control, closes/reopens it, visits Library/Explore/Studio and returns to Learn. It requires the draft and source selection to survive. A separate native editor round trip checks that selected-event and undo history survive view teardown. Coach typing has MIDI and shortcut guards. The Swift 6 runner activates only the child it launched so an accessory preview exposes its accessibility tree reliably. It never targets a user's existing app. Reports must contain the required action results; screenshots alone cannot satisfy the gate. These actions do not test VoiceOver speech, a complete keyboard route, or physical devices. Complete the hands-on matrix in [Device testing](DEVICE_TESTING.md) before claiming those outcomes.

Device boundary tests use injected input, permission responses and a clock. They cover refusal, cancelled starts, grant-after-stop, an old refusal after a new start, background buffer delivery, stale callbacks, held pitch, silence and transcription finalisation. They do not grant/deny real macOS permissions. Settings/catalogue tests use memory storage and a fake sender; paid-reply tests retain a received result across disk failure and reject cancelled/stale completions. Renderer tests check the actual Objective-C delegate selector, main-frame ownership and malformed/nonfinite layouts. Request probes and mutable fault controls have explicit actor ownership; do not add unchecked Sendable or actor assumptions to make migration green.

Window-level Space-key routing runs inside the launched native app host, in both production and instrumented self-checks. It creates two private fixture windows and checks timestamp forwarding, repeats, modifiers, text focus, inactive/detached views, other keys/windows and monitor cleanup. It is required even with audio-output/accessibility skips. Command-line unit tests retain timing and rhythm policy; they do not initialise NSApplication to create windows.

The native self-check opens a MIDI client before audio setup and retains it through the complete run. It requires `midiClientRetained` as well as actual virtual notes, releases and timestamps. A framework/client error is reported directly rather than hidden behind missing downstream checks. A MIDI startup failure is never converted to a skip or an automatic retry. Keep the client alive while doing other work; disposing the last one can let MIDIServer idle out and invalidate the process's CoreMIDI connection.

Snapshot checks wait for the SwiftUI window before applying preview-only activation policy and capture sizes. Missing windows/bitmaps fail explicitly; scene geometry, workspace mounting and capture phases are logged, and asynchronous capture is bounded. Production course-map and score/cursor captures run before accessory self-checks, then the complete suite runs afterward; launch history cannot substitute for first-launch evidence. Preview cursor assertions travel in the renderer's ready message, so a resize cannot overwrite ready data while its checks are still arriving through another native callback. JavaScript boundary tests cover coherent readiness, superseded loads, cursor errors and ordinary playback without diagnostic cursor movement. Editor geometry assertions similarly travel in each render’s ready message, including resize. Long-score scroll proof awaits an internal redraw without publishing an intermediate ready or recursively invoking the native verification callback. Ordinary editor use does not run this diagnostic exercise. On a process timeout, the verifier attempts a one-second stack sample of its own child before terminating that process group. Sampling failure cannot prevent cleanup. These logs are diagnostic evidence, not a substitute for required screenshots and assertion sidecars.

GitHub checks window creation before the full app build with a tiny original SwiftUI scene. The probe uses the same window-sizing policy and native argument encoder as the app verifier, records physical/visible screen bounds and requires a main-capable window. It deliberately puts a presence flag before the output option. Every presence flag gets an explicit YES value: otherwise macOS can consume the next option name as its value and treat the remaining path as a document-open request, suppressing the initial scene. Regression tests cover option order, literal values, missing values and every registered native scenario. The accessibility runner likewise pairs its two presence flags. Minimum and initial window sizes fit the visible display, with room for system chrome; pure tests cover large, small, missing and invalid dimensions. This host check supplements every required Cadence screenshot, renderer assertion and coverage gate. Preview processes retain direct child-process ownership, bounded deadlines and scoped cleanup.

## Snapshot framing budgets

SnapshotFraming separates scheduled UI actions from readiness. Static verified views get a 0.6-second layout opportunity before waiting on the same renderer/domain assertions checked externally. Scrolling, delayed sheets and live edits get 3.5 seconds, and actual accessibility work retains its 30-second allowance. Manual snapshots retain ten seconds; the three Settings captures retain their existing two-second allowance. The 25-second assertion deadline, capture deadline, isolated processes and two-build matrix are unchanged. New delayed preview actions must be added to the framing policy and tested. Guitar picking adds seven native scenarios for styles, clean-note setup, creative arrangement and independent recall.

## Four-process static capture scheduling

`--preview-jobs 4` overlaps two static scenario pairs, with at most four app processes. `1` retains fully serial captures; `2` retains one production/instrumented pair at a time. Accessibility actions and the editor navigation round trip drain previous work and run alone. Device self-checks, first-launch checks and Settings remain outside outer batching; Settings keeps its existing maximum of two processes. Every capture has its own app process, logs, sidecar, storage and profile path. A failed batch joins its other bounded children before returning an error.

The matrix still runs every production and instrumented scenario and the same source/profile inventory and coverage gates. `previewMatrixSeconds` is the matrix's wall time; overlapping `previewPairSeconds` values must not be summed as wall time in four-process mode. Use full local and hosted runs to choose concurrency; injected tests establish barriers, failure cleanup and result separation, not graphical-host capacity.


## Acoustic phrase regression boundary

Synthetic tests feed AVAudioPCMBuffer and AVAudioTime through the same input callback used by phrase capture. They cover loopback estimation and one offset correction, channel selection, sample/host agreement, cumulative drift, missing samples, overflow, clipping and sparse out-of-range PCM, count-in contamination, truncated input, permission failure, configuration changes, interrupted encounters and save-only recovery. Core tests separately cover window ownership, uncertain/disputed matches, stale source archival, independent-return eligibility and original timestamp provenance. No actual microphone permission, acoustic accuracy or USB-interface compatibility is inferred from these fixtures.

Seven native phrase previews exercise linked notation/tab, focused context, uncertainty, independent recall, contextual coaching a compact window and a score-focused layout in both builds. Their fixtures are original synthetic evidence and never open an input device or issue an AI request. Follow the manual device matrix before a hardware-support claim.

## Connected daily-session checks

Daily-session core and integration regressions cover piano/guitar source identity, exact pitch order without timing claims, replays/reveals and re-arming, focus/context, pending-save recovery, unkept interruption exposure, changed sources, first-transfer source visits, creative-artifact identity and spaced eligibility. Original native previews cover piano and guitar, compact focused notation/tab, an uncertain take, Studio, completion, familiar recall and unfamiliar transfer.

The daily-ear-accessibility scenario uses the shared own-child AX driver. It presses the actual listening/imagination/MIDI/check controls, follows a deliberately wrong virtual take into a focus and whole-phrase return, opens the musical answer in Studio, returns to the daily session, opens the full score and resumes from the map. Only this isolated preview injects virtual MIDI and silent demonstration output; it proves control/state integration, not acoustic/MIDI hardware performance. Both accessibility scenarios run serially and are explicitly omitted with --skip-accessibility; CI records both names. No raw audio or paid model request is involved.

The coach draft check reads back its entered question and waits for the inspector's editor to disappear before reopening it or changing sections. An accepted AXPress only acknowledges action dispatch; it does not establish that the closing transition has completed. These observable barriers keep the draft assertion separate from inspector animation timing, without adding retries or fixed delays.
